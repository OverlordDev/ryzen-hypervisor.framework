# Фаза 2: память гостя из памяти процесса

Цель: гость исполняет и читает память, которая принадлежит **userland-процессу** (то, что делают
`hv_vm_map` / `hv_vm_unmap` / `hv_vm_protect`), а нарушения прав приходят как NPT-fault, который
процесс может обработать и повторить инструкцию.

> **Статус: пройдена на железе (5800H): `rhv-map-test` печатает `PASS: all stages`.** Хост-тесты дерева NPT (`tests/npt_test.cpp`) проверяют логику, а закрепление страниц, NPF и `protect`/`unmap` подтверждены реальным запуском. `make test`
> гоняет `tests/npt_test.cpp` (ASan + UBSan). Часть про IOMemoryDescriptor, закрепление страниц и
> реальный NPF проверяется только на железе: `sudo rhv-map-test`. Не запускай, пока фаза 1
> (`rhv-guest-test` печатает `PASS`) не прошла у тебя.

## Как это устроено

```
VmMap(uva, gpa, size, flags)
  └─ IOMemoryDescriptor::withAddressRange(uva, size, task)      процесс вызывающего
       └─ prepare()                                              страницы закреплены (wired)
            └─ getPhysicalSegment() по кускам                    физические адреса
                 └─ Npt::map(gpa + i*4K, pa + i*4K, perm, backing)   по странице, всё или ничего
```

- **Backing** это закреплённый буфер со счётчиком живых страниц. Каждая запись NPT помнит свой
  backing (указатель лежит в листе дерева). Когда последняя страница снята, буфер открепляется
  (`complete`) и отпускается. Поэтому работает **частичный `unmap`** середины или края отображения.
- `map` атомарен: сначала проверяется, что весь диапазон свободен, при любой ошибке в середине
  уже поставленные страницы снимаются. Перекрытие даёт `kIOReturnBusy`.
- `unmap` терпит дыры в диапазоне. `protect` требует, чтобы все страницы были отображены, и тогда
  меняет их все; иначе ничего не меняет (`kIOReturnNotFound`).
- Пустые таблицы страниц освобождаются сразу (`Npt::prune`), так что ВМ, у которой всё снято,
  держит одну страницу корня.
- TLB: `tlbCtl = FLUSH_ALL` на каждом `VMRUN`, поэтому отдельных инвалидаций после
  `unmap`/`protect` не нужно. Менять таблицы можно только пока гость не запущен: `VmRun` держит
  тот же замок.
- `VmMap` принимает адрес только из процесса, который открыл соединение (`current_task() == owner`).
  Иначе процесс, которому передали порт соединения, мог бы закрепить чужие адреса.

### Права

`RHV_MEM_READ/WRITE/EXEC` совпадают с `hv_memory_flags_t`. x86 не умеет «только запись» и
«только исполнение», поэтому `WRITE` и `EXEC` подразумевают `READ`. Права `0` допустимы в
`VmProtect`: страница остаётся отображённой, но любой доступ даёт fault. Исполнение
запрещается битом NX в NPT, он действует при `EFER.NXE=1` на хосте (в macOS это так).

### Причина NPF

`info1` это код ошибки как у `#PF`, `info2` это **гостевой физический адрес** (проверено на Zen 3, 5800H: адрес приходит точным, вместе со смещением внутри страницы):

| бит `info1` | смысл | хелпер |
|---|---|---|
| 0 | страница была отображена, не хватило прав | `rhv_npf_present` |
| 1 | запись | `rhv_npf_is_write` |
| 4 | выборка инструкции | `rhv_npf_is_fetch` |
| 33 | fault при чтении **гостевых** таблиц страниц (а не данных) | `rhv_npf_in_walk` |

Обработчик в userland: посмотреть адрес, `VmMap` / `VmProtect`, запустить `VmRun` с `skip=0`
(инструкция повторится).

## Как запустить

```
make kext tools DEBUG=1
sudo ./build/rhv-map-test
./build/rhv-info stats       # vmMaps, vmUnmaps, vmProtects, vmNptFaults, vmPagesMapped
```

`rhv-map-test` идёт по семи этапам и печатает `ok:` / `FAIL` по каждой проверке: запись гостя
видна в твоём буфере; `protect` даёт fault; ленивый `map` из обработчика; `unmap` и подмена
буфера; отказы на плохие аргументы; ВМ без встроенной памяти; счётчик закреплённых страниц
после `VmDestroy` вернулся к исходному (нет утечки).

## Как читать сбои

| симптом | что это значит |
|---|---|
| `VmMap` возвращает `kIOReturnVMError` | адрес пользователя не отображён или нет прав на запись; либо `getPhysicalSegment` дал 0 |
| `VmMap` возвращает `kIOReturnBusy` | диапазон пересекается с уже отображённым (в том числе со встроенной 1 МиБ) |
| `VmMap` возвращает `kIOReturnNoMemory` | не хватило страниц под таблицы NPT; на 1 ГиБ уходит около 4 МиБ таблиц + служебная память |
| этап 2 `FAIL ... no NPF` | гость записал в read-only страницу: проверь, что `normalizePerm`/NPT-запись выставляют `RW=0`, и что у хоста нет `CR0.WP`-особенностей |
| этап 6 `FAIL ... fetch fault` | NX в NPT не действует; смотри `EFER.NXE` хоста |
| `stage 7 FAIL: counter` | утечка закреплённых страниц: ищи путь, где `dropPage` не вызван |

## Что не сделано

- Нет больших страниц (2 МиБ / 1 ГиБ): каждая гостевая страница стоит одну запись и 8 байт
  служебной памяти. ВМ на 8 ГиБ это порядка 32 МиБ таблиц; для QEMU приемлемо, оптимизировать позже.
- Нет ограничения суммарного размера отображений на пользователя (только `RHV_MAP_MAX_SIZE` на вызов).
- Гость пока не умеет paging в long mode с прерываниями: критерий готовности roadmap
  («гость с paging исполняет код из замапленной памяти») закроет фаза 3 вместе с инъекцией прерываний и
  состоянием FPU. Этап `rhv-map-test` покрывает то, что нужно от NPT для этого.
